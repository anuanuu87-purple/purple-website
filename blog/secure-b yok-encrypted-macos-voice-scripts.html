Implement End‑to‑End BYOK Encryption for macOS Voice‑Driven Automation Scripts

Published on October 17, 2026 • 6 min read

Implement End‑to‑End BYOK Encryption for macOS Voice‑Driven Automation Scripts – In modern macOS workflows, developers and power users increasingly rely on voice‑driven automation to eliminate repetitive mouse clicks and keystrokes. The convenience, however, introduces a new attack surface: script payloads that contain credentials, proprietary logic, or personal data can be intercepted if they are stored or transmitted in clear text. “Bring‑Your‑Own‑Key” (BYOK) encryption lets you retain exclusive control over the cryptographic keys that protect these voice scripts, ensuring that only your trusted environment can decrypt and execute them. This guide walks you through the entire lifecycle – from key generation to secure execution – using native macOS tools and the Purple autonomous OS AI, which natively supports BYOK‑protected voice workflows.

Understanding BYOK Encryption for Voice Scripts

What is BYOK?

BYOK (Bring‑Your‑Own‑Key) is a security model where the data owner generates, stores, and manages the encryption keys rather than relying on a third‑party provider. In the macOS context, BYOK leverages the Secure Enclave and Keychain Services to keep private keys isolated from the operating system’s default encryption mechanisms. By using BYOK, you guarantee that even if the host system is compromised, the attacker cannot decrypt your voice script payloads without the key you control.

Why Voice‑Driven Automation Needs Encryption

Voice‑driven automation scripts often contain:

  • Sensitive API tokens for cloud services.
  • Personal identifiers used in PDF summarization or document drafting.
  • File system paths that expose corporate data structures.

When these scripts are stored on disk or transmitted to a voice‑assistant service, they become attractive targets. Encrypting the script payloads with a BYOK key ensures confidentiality at rest and in transit, while still allowing the Purple AI to decrypt them on‑the‑fly only after successful voice authentication.

macOS Security Foundations

macOS provides three core primitives that make BYOK practical:

  1. Keychain Access – A secure vault that stores passwords, certificates, and private keys with ACLs tied to the user’s login credentials.
  2. Secure Enclave – A hardware‑isolated coprocessor that can generate and store cryptographic keys that never leave the chip.
  3. FileVault 2 – Full‑disk encryption that protects data at rest, but does not replace the need for application‑level encryption of script payloads.

By combining these primitives, you can create a layered defense where the BYOK key lives in the Secure Enclave, is referenced via Keychain, and encrypts the voice script files that Purple later decrypts for execution.

Preparing Your macOS Environment

Install Required Tools

The implementation relies on standard macOS utilities and a few open‑source packages. Open Terminal and run:

# Install Homebrew if not present
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# Install OpenSSL (for modern cipher suites)
brew install openssl

# Install jq for JSON handling (used by Purple’s API)
brew install jq

# Verify installations
openssl version
jq --version

Generating Your Own Encryption Keys

Use the Secure Enclave to generate an RSA‑4096 key pair that will never leave the hardware module. The following command stores the private key in the Keychain under the label com.mycompany.voice.byk:

security create-keychain -p "" ~/Library/Keychains/VoiceBYOK.keychain
security set-keychain-settings -t 3600 -u ~/Library/Keychains/VoiceBYOK.keychain

# Generate RSA key pair with Secure Enclave
security add-generic-password -a "$(whoami)" -s "VoiceBYOKPublic" -w "$(openssl rand -base64 32)" ~/Library/Keychains/VoiceBYOK.keychain

security import /dev/stdin -k ~/Library/Keychains/VoiceBYOK.keychain -P "" -T /usr/bin/openssl <<EOF
-----BEGIN RSA PRIVATE KEY-----
$(openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -outform PEM)
-----END RSA PRIVATE KEY-----
EOF

After execution, the private key resides securely in the Keychain, while the public key can be exported for script encryption:

security export -k ~/Library/Keychains/VoiceBYOK.keychain -t pub -f pem -o voice_public.pem -P ""

Configuring Secure Storage with Keychain

To keep the encryption passphrase out of plain sight, store it as a generic password item:

security add-generic-password -a "$(whoami)" -s "VoiceScriptPassphrase" -w "SuperSecretPassphrase123!" ~/Library/Keychains/VoiceBYOK.keychain

Later, retrieve it programmatically when decrypting a script:

PASSPHRASE=$(security find-generic-password -a "$(whoami)" -s "VoiceScriptPassphrase" -w ~/Library/Keychains/VoiceBYOK.keychain)

Building and Encrypting Voice Scripts

Writing a Sample Voice Script with Purple

Below is a minimal Purple script that fetches the latest headlines from a news site, summarizes them, and writes the result to a Markdown file. Save the plain‑text version as news_summary.txt for encryption.

# Purple script: news_summary.txt
# Voice command: “Purple, summarize today’s tech news”

fetch "https://news.ycombinator.com/rss" \
| parse_rss \
| filter keyword="technology" \
| summarize length=200 \
| write "/Users/$(whoami)/Documents/TechNewsSummary.md"

Encrypting Script Payloads with OpenSSL

Encrypt the script using the public key generated earlier. The command produces a binary ciphertext file (news_summary.enc) that can be safely stored in any directory.

openssl rsautl -encrypt -inkey voice_public.pem -pubin -in news_summary.txt -out news_summary.enc

For larger scripts, combine symmetric encryption (AES‑256‑GCM) with the RSA key to avoid RSA size limits:

# Generate a random session key
openssl rand -base64 32 > session.key

# Encrypt the script with AES‑256‑GCM
openssl enc -aes-256-gcm -salt -in news_summary.txt -out news_summary.aes -pass file:session.key

# Encrypt the session key with RSA
openssl rsautl -encrypt -inkey voice_public.pem -pubin -in session.key -out session.key.enc

# Package both encrypted parts
cat session.key.enc news_summary.aes > news_summary.pkg

The .pkg file can be placed in ~/Library/Application Support/Purple/Scripts/ where Purple expects encrypted assets.

Storing Encrypted Scripts Securely

Set restrictive file permissions so that only your user account can read the encrypted payload:

chmod 600 ~/Library/Application\ Support/Purple/Scripts/news_summary.pkg

Optionally, add the script directory to the Keychain’s “access control list” so that decryption can only be triggered after successful voice authentication:

security set-keychain-settings -t 3600 -u ~/Library/Keychains/VoiceBYOK.keychain
security add-trusted-cert -d -r trustRoot -k ~/Library/Keychains/VoiceBYOK.keychain ~/Library/Application\ Support/Purple/Certificates/purple_ca.pem

Deploying and Executing Encrypted Scripts via Voice

Registering Scripts with Purple’s BYOK API

Purple provides a REST endpoint for script registration. Use the stored private key to sign the registration payload, guaranteeing authenticity.

#!/bin/bash
# Register encrypted script with Purple
SCRIPT_ID="news_summary_$(date +%s)"
PAYLOAD=$(jq -n \
  --arg id "$SCRIPT_ID" \
  --arg path "$HOME/Library/Application Support/Purple/Scripts/news_summary.pkg" \
  '{id:$id, path:$path}')

# Sign payload with private key from Keychain
SIGNATURE=$(echo -n "$PAYLOAD" | openssl dgst -sha256 -sign <(security find-keychain -a "$(whoami)" -s "com.mycompany.voice.byk") | base64)

curl -X POST https://api.purple.ai/v1/scripts/register \
  -H "Content-Type: application/json" \
  -d "$(jq -n \
        --argjson payload "$PAYLOAD" \
        --arg sig "$SIGNATURE" \
        '{payload:$payload, signature:$sig}')"

The response contains a scriptToken that Purple uses to locate and decrypt the script at runtime.

Voice Command Syntax and Runtime Decryption

Once registered, invoke the script with a natural language phrase. Purple internally performs these steps:

  1. Validate the user’s voiceprint against the stored biometric profile.
  2. Retrieve the encrypted payload from the script directory.
  3. Decrypt the session key using the Secure Enclave‑protected RSA private key.
  4. Decrypt the script body with AES‑256‑GCM.
  5. Execute the plaintext script in a sandboxed interpreter.

From the user’s perspective, the command is as simple as:

“Purple, run the tech news summary.”

Auditing Execution Logs

For compliance, enable verbose logging in Purple and forward logs to the macOS Unified Logging system:

defaults write com.purple.ai LoggingLevel -int 5
log stream --predicate 'process == "Purple"' --info

Each log entry includes a timestamp, the script ID, and a hash of the decrypted payload, allowing you to verify that no tampering occurred between registration and execution.

Comparison: BYOK vs Built‑in macOS Encryption Options

The table below highlights why BYOK is the preferred model for voice‑driven automation, especially when integrating with Purple:

  • Control of Keys
    • BYOK: Keys generated and stored in Secure Enclave; never leave the device.
    • FileVault: System‑wide key derived from user password; shared across all data.
    • Keychain‑only: Good for passwords but not for bulk script encryption.
  • Granular Access
    • BYOK: Per‑script ACLs via Keychain items.
    • FileVault: All‑or‑nothing access once the user logs in.
  • Compliance Fit
    • BYOK: Meets GDPR, CCPA, and industry‑specific key‑management requirements.
    • Standard macOS encryption: May not satisfy external audit mandates.
  • Performance
    • BYOK: One‑time RSA decryption of a small session key; bulk AES decryption is fast.
    • FileVault: Full‑disk decryption overhead on boot only.
  • Integration with Voice AI
    • BYOK: Purple can request the Secure Enclave to decrypt on‑demand, preserving zero‑knowledge to the OS.
    • Native macOS tools: No built‑in voice‑assistant hook for per‑script decryption.

Frequently Asked Questions

Can I rotate my BYOK key without re‑encrypting every script?

Yes. Store the encrypted session keys separately from the script payload. When you generate a new RSA key pair, decrypt the existing session keys with the old private key, re‑encrypt them with the new public key, and update the .pkg container. The script body remains unchanged because it is encrypted with the symmetric session key.

What happens if the Secure Enclave is disabled (e.g., on a Mac without T2 chip)?

On Intel Macs without a T2 chip, the Secure Enclave is unavailable, but you can still achieve BYOK‑level security by using the macOS Keychain with a strong passphrase and enabling require user presence for key access. The trade‑off is reduced hardware isolation, so you should enforce stricter OS‑level hardening (e.g., enable System Integrity Protection and Gatekeeper).

Is it safe to store the encrypted script files in iCloud Drive?

Encrypted payloads can be synced via iCloud without exposing plaintext, provided the encryption keys never leave the local device. Ensure that the private RSA key remains in the local Secure Enclave and that the iCloud container does not have write‑back permissions that could allow a compromised device to push a malicious script version. Regularly audit the iCloud folder for unexpected files.
